# Section 2. 객체 지향 설계와 스프링

> 학습 메모를 바탕으로 정리한 내용입니다. 현재 프로젝트의 회원 예제와 연결해 복습합니다.

## 1. 스프링과 스프링 부트

- **스프링 프레임워크**는 DI 컨테이너, AOP, 이벤트 등 애플리케이션 개발에 필요한 기능을 제공합니다.
- **스프링 부트**는 스프링 애플리케이션을 편리하게 만들고 실행할 수 있도록 자동 설정과 의존성 관리 등을 지원합니다.
- 스프링 부트를 사용하면 설정 부담을 줄이고 독립적으로 실행할 수 있는 애플리케이션을 쉽게 만들 수 있습니다.

## 2. 객체 지향과 다형성

객체 지향에서는 각 객체가 협력하며 기능을 수행합니다. **다형성**을 이용하면 같은 역할을 가진 여러 구현체를 하나의 타입으로 다룰 수 있습니다.

뮤지컬의 배역을 생각해 보면, 배역은 **역할**, 그 배역을 맡는 배우는 **구현**에 비유할 수 있습니다. 배우가 바뀌어도 배역의 대사와 약속을 지킨다면 공연은 이어질 수 있습니다.

현재 프로젝트에서는 다음과 같이 대응됩니다.

| 구분 | 회원 예제 | 의미 |
| --- | --- | --- |
| 역할 | `MemberRepository` | 회원 저장과 조회에 관한 약속 |
| 구현 | `MemoryMemrberRepository` | 메모리의 `Map`에 회원을 저장하고 조회 |
| 클라이언트 | `MemberServiceImpl` | 저장소를 이용해 회원 가입과 조회 수행 |

예를 들어 `MemberRepository repository = new MemoryMemrberRepository();`처럼 인터페이스 타입으로 구현 객체를 참조할 수 있습니다. `repository.save(member)`를 호출하면 실제 객체인 `MemoryMemrberRepository`의 `save()`가 실행됩니다.

다만 **다형성만 사용한다고 구현체 교체가 자동으로 되는 것은 아닙니다.** 클라이언트가 `new`로 구현 클래스를 직접 선택한다면 구현체를 바꿀 때 클라이언트 코드도 바꿔야 합니다.

## 3. SOLID: 좋은 객체 지향 설계의 다섯 원칙

### SRP — 단일 책임 원칙

한 클래스는 하나의 책임을 가져야 합니다. 책임의 크기는 상황에 따라 달라지므로 **변경할 이유와 변경에 따른 파급 효과**를 기준으로 생각합니다.

회원 가입 로직과 회원 저장 방식을 분리하면, 저장 방식을 바꿀 때 가입 로직에 미치는 영향을 줄일 수 있습니다. 다만 단순히 메서드 수가 적다고 SRP를 지킨 것은 아닙니다.

### OCP — 개방-폐쇄 원칙

소프트웨어 요소는 **확장에는 열려 있고, 변경에는 닫혀 있어야 한다**는 원칙입니다. 새 저장 방식을 추가할 수 있으면서도 기존 회원 서비스의 코드를 되도록 바꾸지 않는 것을 목표로 합니다.

현재 서비스는 다음처럼 저장소를 직접 생성합니다.

```java
private final MemberRepository memberRepository = new MemoryMemrberRepository();
```

나중에 DB 저장소를 만든다면, 위 코드를 수정해야 교체할 수 있습니다. 인터페이스를 사용했지만 **구현체 선택까지 서비스가 담당하므로**, 이 지점에서 OCP를 만족하기 어렵습니다. 객체를 생성하고 연결하는 책임을 별도로 분리하면 서비스 코드를 유지하면서 연결할 구현체를 바꿀 수 있습니다.

> OCP는 어떤 변경에도 코드 수정이 전혀 없어야 한다는 뜻이 아닙니다. 예상하는 확장에 대해 기존 핵심 코드를 안정적으로 유지하는 것이 목표입니다.

### LSP — 리스코프 치환 원칙

하위 타입의 객체를 사용해도 상위 타입이 약속한 동작과 프로그램의 정확성이 유지되어야 합니다. **컴파일 성공뿐 아니라 기능적인 약속도 지켜야 합니다.**

예를 들어 `MemberRepository`의 구현체가 저장한 회원을 ID로 조회할 수 있다는 약속을 한다면, 메모리 저장소든 DB 저장소든 그 약속을 지켜야 클라이언트가 안심하고 교체할 수 있습니다.

### ISP — 인터페이스 분리 원칙

클라이언트가 사용하지 않는 기능까지 포함한 거대한 인터페이스에 의존하기보다, **필요에 맞게 나뉜 인터페이스**가 낫다는 원칙입니다.

예를 들어 회원 조회만 필요한 클라이언트와 회원 관리 기능이 필요한 클라이언트의 요구가 충분히 다르다면, 조회 역할과 관리 역할을 나누는 것을 고려할 수 있습니다. 무조건 잘게 나누기보다는 실제 사용과 변경 방향을 기준으로 판단합니다.

### DIP — 의존관계 역전 원칙

고수준의 정책을 담은 코드가 구체적인 구현에 직접 묶이기보다 **추상화에 의존**하도록 설계하는 원칙입니다.

현재 `MemberServiceImpl`은 필드 타입으로 `MemberRepository`를 사용하지만, 동시에 `new MemoryMemrberRepository()`로 구현 클래스도 직접 알고 있습니다. 따라서 추상화와 구체화 모두에 의존합니다.

생성자를 통해 저장소를 전달받으면 서비스 코드에서 직접 구현체를 선택하지 않아도 됩니다.

```java
// 이해를 돕기 위한 예시: 현재 프로젝트 코드를 변경한 것은 아닙니다.
public class MemberServiceImpl implements MemberService {
    private final MemberRepository memberRepository;

    public MemberServiceImpl(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```

이제 서비스는 `MemberRepository` 역할을 사용하고, **어떤 구현체를 만들고 전달할지는 외부**에서 결정합니다. 단, 실제 애플리케이션 어딘가에서는 여전히 구체 객체를 생성하고 연결해야 합니다.

## 4. IoC, DI, DI 컨테이너

- **IoC(제어의 역전)**: 객체가 프로그램의 흐름이나 필요한 협력 객체의 생성·연결을 직접 제어하기보다 외부에 맡기는 설계 관점입니다.
- **DI(의존관계 주입)**: 객체가 필요한 협력 객체를 직접 만들지 않고 외부에서 전달받는 방법입니다. 생성자 주입이 대표적입니다.
- **DI 컨테이너**: 객체를 생성하고 의존관계를 연결하는 역할을 담당합니다. 스프링 컨테이너가 이 역할을 지원합니다.

```text
현재: MemberServiceImpl → 직접 new → MemoryMemrberRepository

DI 예시: 조립하는 곳 → 저장소 생성 → MemberServiceImpl 생성자에 전달
                                   ↓
                       서비스는 MemberRepository 사용
```

스프링 컨테이너를 사용하면 객체 생성과 연결을 스프링에 맡길 수 있습니다. 하지만 **DI 자체는 스프링 없이도 가능**하며, 스프링을 사용한다고 SOLID가 자동으로 지켜지는 것도 아닙니다. 역할과 책임을 어떻게 나누는지가 중요합니다.

## 5. 인터페이스는 언제 도입할까?

역할과 구현을 분리하면 구현체 교체와 테스트에 유리하지만, 인터페이스도 이해하고 관리해야 하는 추상화 비용이 있습니다. 변경·확장 가능성이 낮고 추상화의 이점이 작다면 구체 클래스를 먼저 사용하고, 필요할 때 인터페이스를 도입하는 것도 가능합니다.
